# Сценарій захисту архітектури системи управління файлами

## 1. Діаграма прецедентів (Use Case Diagram)
* **Що демонструє:** Визначає межі нашої системи та ключові сценарії взаємодії користувача з файловим сховищем.
* **Рішення:** Ми об'єднали дрібні UI-дії у загальні бізнес-прецеденти (наприклад, "Manage Dashboard View") та винесли авторизацію як обов'язкову передумову (`<<include>>`) для абсолютно всіх файлових операцій.
* **Обґрунтування:** Такий рівень абстракції дозволяє команді сфокусуватися на реалізації критичного бізнес-функціоналу, уникаючи передчасної деталізації інтерфейсу, що гарантує швидкий вихід на повноцінний MVP без зриву строків.

## 2. Загальна діаграма класів (Class Overview Diagram)
* **Що демонструє:** Статичну структуру бекенду та клієнтських додатків із логічним розподілом на шари Client, Server API та Database.
* **Рішення:** Ми свідомо обрали монолітну серверну архітектуру навколо FastAPI та жорстку композицію (`ON DELETE CASCADE`) між сутностями `User` та `File` в ORM-моделі.
* **Обґрунтування:** Це прагматичне рішення мінімізує накладні витрати на інтеграцію та інфраструктуру (порівняно з мікросервісами), забезпечуючи при цьому абсолютну цілісність даних без складної транзакційної логіки.

## 3. VOPC-діаграма для сортування/фільтрації (Class VOPC)
* **Що демонструє:** Взаємодію класів за патерном Boundary-Control-Entity (BCE) під час керування відображенням файлів на клієнті.
* **Рішення:** Ми об'єднали логіку фільтрації та сортування в єдиний компонент `SortFilterController`, який працює з денормалізованим атрибутом `extension` сутності `File`.
* **Обґрунтування:** Зберігання розширення файлу як окремого поля та єдиний контролер суттєво пришвидшують SQL-запити та спрощують клієнтський код, позбавляючи нас від "важкого" парсингу рядків на льоту.

## 4. Діаграма активності синхронізації (Activity Diagram)
* **Що демонструє:** Покроковий алгоритм паралельної двосторонньої синхронізації папок між локальним десктоп-клієнтом та сервером.
* **Рішення:** Ми реалізували стратегію "Server-authoritative", де сервер одноосібно порівнює маніфести, а локальні файли автоматично не видаляються задля безпеки.
* **Обґрунтування:** Відмова від складного розв'язання конфліктів на клієнті зводить до мінімуму ризик втрати даних користувача і дозволяє реалізувати надійний механізм синхронізації за лічені дні замість тижнів.

## 5. Діаграма послідовності Upload (Sequence Upload Diagram)
* **Що демонструє:** Взаємодію компонентів у часі під час завантаження користувачем файлу на бекенд.
* **Рішення:** Ми запровадили ранню валідацію токенів доступу та жорсткий контроль ліміту розміру файлу (50 МБ) через альтернативний фрейм (`alt`) ще до початку збереження бінарних даних на диск.
* **Обґрунтування:** Цей підхід захищає нашу інфраструктуру від перевантажень пам'яті (DDoS великими файлами) найдешевшим і найшвидшим інженерним способом.

## 6. Діаграма послідовності Sync (Sequence Sync Diagram)
* **Що демонструє:** Технічний протокол масової синхронізації з використанням циклічних конструкцій (`loop`) для завантаження та скачування.
* **Рішення:** Замість складних WebSocket-з'єднань ми обрали пакетну обробку через стандартний HTTP REST, де клієнт ітерує по дельті та виконує точкові атомарні запити.
* **Обґрунтування:** Використання простих REST-запитів робить синхронізацію стійкою до обривів мережі та дозволяє нам розгорнути стабільний клієнт, не ускладнюючи серверну частину підтриманням постійних з'єднань.

## 7. Діаграма станів файлу (State Machine Diagram)
* **Що демонструє:** Життєвий цикл файлового активу від моменту його створення до остаточного видалення.
* **Рішення:** Ми виділили транзитний стан `Syncing` для тривалих мережевих операцій та забезпечили можливість видалення файлу практично з будь-якого іншого стабільного стану.
* **Обґрунтування:** Явне управління станом "Синхронізується" блокує стан гонитви (race conditions) під час паралельного редагування, гарантуючи передбачуваність клієнтського додатка.

## 8. Діаграма компонентів (Component Diagram)
* **Що демонструє:** Структуру фізичних модулів системи та залежності між ними через абстрактні інтерфейси.
* **Рішення:** Архітектура чітко розмежовує незалежні веб- та десктоп-клієнти, які комунікують з інкапсульованим сервером виключно через стандартизований інтерфейс `HTTP / REST`.
* **Обґрунтування:** Така строга модульність дозволяє розробляти десктоп, веб-інтерфейс та бекенд повністю паралельно, що є критично важливим для дотримання жорстких графіків розробки.

## 9. Діаграма розгортання (Deployment Diagram)
* **Що демонструє:** Фізичну топологію розміщення артефактів системи на апаратному забезпеченні клієнтів та серверів.
* **Рішення:** Ми свідомо відмовилися від складних хмарних кластерів на користь єдиної Cloud VM, де FastAPI-додаток працює у зв'язці з вбудованою базою SQLite (`data.db`) та локальною файловою системою.
* **Обґрунтування:** Використання конфігурації з SQLite гарантує нульові витрати на адміністрування бази даних і дозволяє підняти повноцінне production-оточення за лічені хвилини, ідеально підходячи для цілей цього проєкту.
